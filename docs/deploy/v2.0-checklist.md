# Despliegue de v2.0 — checklist del dueño

v2.0 está entera en `staging`. Pasarla a producción es una decisión del dueño del repo:
- se promueve `staging` → `main` con un PR;
- al mergear, CI corre `migrate-and-deploy` (`alembic upgrade head` contra Supabase y el deploy de Render);
- Vercel publica el frontend desde la rama de producción que tenga configurada (`main`).

Seguir los pasos en orden. Ninguno lo hace un agente.

## 1. Antes de promover

- [ ] **Backup de Supabase.** GitHub → Actions → **Backup Supabase to R2** → *Run workflow* con label `pre-v2.0` (ver [`docs/backups.md`](../backups.md)). Confirmar que el archivo está en R2.
- [ ] **Datos que frenan migraciones.** Tres migraciones abortan (sin aplicar nada) si encuentran datos que no pueden convertir:
  - `f6a7b8c9d0e1` (jugador único por partida): no puede haber un mismo jugador dos veces en una partida.

    ```sql
    select game_id, player_id, count(*) from player_results group by 1, 2 having count(*) > 1;
    ```

  - `f2a3b4c5d6e7` (colores): como máximo 10 jugadores activos.

    ```sql
    select count(*) from players where is_active;
    ```

  - `b8c9d0e1f2a3` (historial de ELO único por partida y jugador): la limpia sola, sin pasos manuales.
- [ ] **Variables de autenticación en Render.** Sin ellas el login responde **503** y el resto de la API **401**, así que nadie puede entrar (fail-closed, D-50). Cargarlas *antes* del merge, en Render → servicio `tm-scorekeeper-backend` → *Environment*:

  | Variable | Cómo generarla |
  |---|---|
  | `AUTH_USERNAME` | El usuario que va a usar el grupo |
  | `AUTH_PASSWORD_HASH` | `cd backend && python -m scripts.hash_password` (pide la contraseña y devuelve el hash PBKDF2) |
  | `AUTH_SECRET` | `python -c "import secrets; print(secrets.token_urlsafe(48))"` (32 caracteres o más) |
  | `ADMIN_SECRET` | Igual que `AUTH_SECRET`, otro valor. Lo pide `POST /admin/recompute` |

  `TRUSTED_PROXY_HOPS=1` ya viene en `render.yaml`. `DATABASE_URL` y `FRONTEND_URL` no cambian.
- [ ] **Vercel.** `VITE_API_URL` sigue apuntando al backend de Render. No hace falta nada nuevo.
- [ ] **Clientes de la API vieja.** v2.0 retira `GET /games/{id}/results|elo|records`, `POST /games/{id}/achievements`, `GET /players/{id}/profile|elo-summary` y `POST /achievements/reconcile` (D-82). Si algo fuera del frontend los usa, pasarlo a `GET /games/{id}/report`, `GET /players/{id}/insights` o `POST /admin/recompute`.

## 2. Promover

- [ ] Abrir un PR `staging` → `main` y esperar CI en verde: backend, migraciones, frontend con presupuesto del bundle y herramientas.
- [ ] Mergear con merge commit.
- [ ] En Actions, mirar el job `migrate-and-deploy`. `alembic upgrade head` tiene que terminar sin error y después dispara el deploy de Render.

## 3. Después del deploy

- [ ] **Recálculo de lo derivado (D-13).** Al arrancar, el backend compara `app_meta.derived_version` con `DERIVED_VERSION` y, si quedó atrás, recalcula ELO y logros desde el historial. En el primer arranque de v2.0 pasa siempre. Para confirmarlo:
  - en Supabase, `select value from app_meta where key = 'derived_version';` tiene que dar `1` (el `DERIVED_VERSION` de `backend/services/derived_service.py`);
  - en los logs de Render no tiene que aparecer `No se pudo verificar derived_version al arrancar`. El aviso de que recalcula es de nivel INFO y Render no lo muestra.

  Si hiciera falta forzarlo:

  ```bash
  curl -X POST "$API/admin/recompute" -H "Authorization: Bearer $TOKEN" -H "X-Admin-Secret: $ADMIN_SECRET"
  ```

- [ ] **Humo** en el teléfono y en la computadora:
  - [ ] `/acceso`: una contraseña equivocada muestra el error; la correcta entra a Inicio.
  - [ ] **Inicio:** temporada, última partida y bitácora con datos reales.
  - [ ] **Partidas:**
    - la cantidad coincide con la de antes;
    - un informe abre con puntaje, ELO, récords y logros.
  - [ ] **Ranking, Perfil, Récords y Logros:** cargan, y el filtro de mesa cambia los datos.
  - [ ] **Registrar:**
    - registrar una partida de prueba muestra la ceremonia;
    - borrarla desde su informe;
    - confirmar que el ranking vuelve a como estaba.
  - [ ] **Sin token, la API responde 401:**

    ```bash
    curl -i "$API/players/"
    ```

  - [ ] **Bloqueo por IP (D-54).** Desde dos redes distintas, un login fallido en cada una no tiene que bloquear a la otra. Si se bloquean juntas, subir `TRUSTED_PROXY_HOPS`.

## 4. Si algo sale mal

- **El frontend falla y el backend anda:** en Vercel, *Promote* el deploy anterior.
- **Una migración abortó** (el job `migrate-and-deploy` falla en `alembic upgrade head`): la base quedó como estaba, porque `alembic upgrade head` corre todas las migraciones en una sola transacción (`db/migrations/env.py`). Revertir el merge en `main`, corregir los datos (paso 1) y volver a promover.
- **Las migraciones se aplicaron y el backend o los datos fallan:** revertir el merge no alcanza. El código viejo no conoce las revisiones nuevas (`alembic upgrade head` falla) y no funciona sobre el esquema nuevo. Hacerlo en este orden:
  1. **Primero la base:** restaurar el backup `pre-v2.0` siguiendo «Restaurar a producción» de [`docs/backups.md`](../backups.md). Es decir, probar antes en una base aparte, avisar al grupo y usar `SUPABASE_DIRECT_URL`, no el `DATABASE_URL` del pooler.
  2. **Después el código:** revertir el merge en `main` y redesplegar el backend anterior (Render → *Manual Deploy* del commit previo).
- **El login responde 503, o todo da 401 con un token recién emitido:** faltan variables de autenticación (paso 1).
